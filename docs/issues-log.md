# Issues log — real problems hit while building, and how they were fixed

| # | Problem | Cause | Fix | Lesson |
|---|---|---|---|---|
| 1 | A planted 6.1m GMRA deficit came out as 4.99m | Random trades gave a requirement smaller than the planted deficit, so posted collateral went negative and was silently clamped to 0 | Re-draw trades until the scenario fits | Check generated data against the scenario it was meant to create, not just that files exist |
| 2 | Generating 200 counterparties hung forever | Large random deficits applied to 2–3-trade books could never fit, so the "re-draw until it fits" loop never ended | Random agreements now derive their target from their own requirement; planted ones get a bounded 500-try retry that fails with a clear error | Never write an unbounded retry loop |
| 3 | Rejected API credentials surfaced as a raw `HTTPError 401` | Token request errors weren't handled separately | Raise `BankApiError("token request rejected – check client secret in Secrets Manager")`, never retried | Error messages should tell the on-call person what to fix |
| 4 | `AttributeError: module 'secrets' has no attribute 'get_secret'` | Our helper was named `secrets.py`, the same as Python's built-in module | Renamed to `secret_store.py` | Never name your own files after standard-library modules |
| 5 | Regenerating the same day produced different SHA-256s for every Excel and PDF file, so landing would have treated unchanged files as corrected re-sends | Excel (a zip) and PDF embed "created/modified now" timestamps; the content was identical but the bytes were not | Pinned PDF output (`rl_config.invariant`) and rewrote Excel zips with a fixed timestamp | A byte hash detects *any* change, including meaningless ones. Real counterparties re-sending the same statement will also produce new bytes, so Bronze must also de-duplicate on business keys (agreement + trade + date), not only on file hash |
| 6 | Two runs with the same seed still differed: one counterparty's email time changed | Late counterparties were picked by looping over a Python `set`, whose order changes between runs (string hash randomisation) | Loop over `sorted(set)` | "Same seed" is only reproducible if iteration order is fixed too |
| 7 | On a Mac, `import reportlab` failed: "reportlab requires 3.10+" | macOS comes with Python 3.9.6, which reached end-of-life in Oct 2025; pip still installed a reportlab release that refuses to run on 3.9 | Installed Python 3.13 with Homebrew and created the virtual environment with it; README now states Python 3.10+ | Pin the Python version a project needs and check it first; the system Python on a Mac is not meant for project work |
| 8 | `terraform apply` failed with `InvalidTag` on 3 of 4 lake buckets | S3 tag values may not contain commas; three "Purpose" tags had them | Removed the commas and re-applied: 24 added, nothing duplicated | `plan` checks syntax, not the cloud's rules. Terraform state kept what had already succeeded, so the re-run only built the rest |
